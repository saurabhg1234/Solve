# Mindmap proposal diagrams

Read `docs/PROPOSAL_DESIGN_STANDARD.md` and `docs/DIAGRAM_WORKFLOW.md` from the repository root. These contain Saurabh's standing visual requirements and the implementation workflow. The native source/template and release contracts in `docs/NATIVE_DOCUMENTS.md` remain separate.

Before drawing, select the reader's question, semantic diagram type, printed dimensions and source-grounded content. Use the provided branding; do not ask for a new palette when a current reference already supplies it. Announce the chosen approach briefly and proceed within the user's authorized scope.

Apply the 17 October client-facing requirements in the design standard: relevant cover artwork, both official logos, Mindmap at the top of every page, an About Mindmap section, and no internal authoring/QC narration in client documents. Vary diagram grammars deliberately; especially consider sequence, lifecycle, evidence comparison and traceability tree diagrams. Adapt requested PowerPoint output to an editable landscape narrative with detailed diagrams in an appendix. Run the client proposal preflight and visually inspect both document and slide exports.

Include the reusable company section from `docs/MINDMAP_COMPANY_SLIDES.md`: what Mindmap does, engineering practices, geographic presence and sourced customers. End with a designed closing/contact slide after any appendix. Treat customer logos as current/past identification, not endorsements, and retain their source qualification.

Use the local helpers in `scripts/visuals`. Prefer explicit actor lanes, distinct decision shapes, real data boundaries, routed exceptions and restrained focal emphasis. Check text at the printed size. For multi-figure proposals supply editable SVGs, a searchable offline HTML atlas and the requested document formats. Render and inspect every final document page and exercise the atlas controls before delivery.
